# Overview
This document is a guide for the SRE team to use the terraform scripts to create AKS cluster. Before you run the script, it is important for you the understand how the code is structured and organized in the folders. So, Let's go over the folder structure first, and then the resource group structure which should explain how we are organizing our azure resources for the AKS cluster.

## DO NOTs
- Do not run terraform command instead use the helper script ./run.sh
- Do not re-run the script once the environment is finalized and verify. (this may break the environment otherwise)

## Pre-requisite Softwares
- WSL (Windows Subsystem Linux - Ubuntu)
- terraform on WSL
- jq on WSL
- kubelogin on WSL
** must run the script from a Linux system.

## Pre-requisite Setups
- Make sure the AAD groups for AKS Admin is already created.
- Make sure you have a storage account already created to store the terraform state.
- Important* - Every project run must be done on a separate terraform state file.

## Folder Structure
1. _source Folder: (stores resource creation scripts)
- main.tf 
- variables.tf (stores the defination of variables)
- resources-<app>tf.  (Each <app> must have its own output file named with a suffix -<app>.tf )
- outputs-<app>tf. (Each <app> must have its own output file named with a suffix -<app>.tf )

2. _configs Folder: (stores the terraform state file configuration)
- backend-<env>-<app>.conf (Each <env> and <app> combination must have its own file suffixed with -<env>-<app>.tf)

3. _modules Folder: (stores the terraform modules. this is to break down and simplify the scripting)
- the codes in the modules folder are same for all environment and app.

4. _variables Folder: (stores the values of variables)
- variables-<env>.tfvars: (Each <env> must have its own output file named with a suffix -<env>.tfvars)

5. _help Fodler:
- stores troubleshooting commands and scripts.

## Resource Group Structure
The AKS cluster is going to the following resource groups organzing the azure resources:
- aksoc-<env>-<location>-rg: this is the primary resource group that will store the AKS cluster, the user created resources that are necessary for the cluster to run. (like vNet, Subnets, Log Analytic Workspace, Load Balancer, etc...)
- aksoc-<env>-<location>-rg-mc: this resource group is auto-generated by the cluster where the cluster stores its system generated resources. 
- aksoc-<env>-<drlocation>-rg: this is same as aksoc-<env>-<location>-rg. It's created if DR environemnt is requested.
- aksoc-<env>-<drlocation>-rg-mc: this is same as aksoc-<env>-<location>-rg-mc.
- aksoc-<env>-<location>-base-rg: There are resources which are common to all applications. This resource group stores them.
- aksoc-<env>-<drlocation>-base-rg: this is same as aksoc-<env>-<location>-base-rg. It's created if DR environment is requested. 
- aksoc-<env>-<location>-<app>-rg: Every application will have its own resource group to store the application specific resources. E.g. aksoc-<env>-<location>-secblogs-rg stores the security blog resources.
- aksoc-<env>-<drlocation>-<app>-rg: It's same as aksoc-<env>-<location>-<app>-rg and it's created if DR environment is requested.

## Disaster Recovery (DR) Notes
There are azure resources which are redundant by design. We have taken that into consideration in order not to create additional resources and optimize the setup from cost perspective. Here are something to note about the azure resources.

- Storage Account (RA-GZRS): Storage account creates its replication in its paired region. (E.g. a store account in eastus creates its replication in westus automatically.). But note, the replication in paired region is always of LRS type. In case you do the failover, please make sure, you update the paired region storage to RA-GZRS if you want it to replicate back into primary source.

- Key Vault: Key Vault creates its replication on its own. In case of region outage, it automatically fails over to its replication. But note, this failover takes 15-20 minutes.

- MySQL Flex Server: MySQL can have a read-only replication. It requires manual intervention to do the failover incase of region outage.


## How to run the script
Note that the terraform script here must be invoked using the helper script (run.sh). 
./run.sh <env> <terraform_verb> 
or
./run.sh <env-app> <terraform_verb> 

<env> : dev, poc, ppe, prd (must be of 3 characters)
<app> : base, riskiq, secblog, etc... 
<terraform_verb>:
 - init: initialize state (terraform init)
 - initupgrade: upgrade initialization file (same as terrraform init -upgrade)
 - apply: create resources (same as terraform apply)
 - plan: build the resource creation plan (same as terrraform plan)
 - destroy: destry resources (same as terraform destroy)

## Setting up an AKS Cluster
Step0: Ensure the following files are existing and is having right configuration.
./_configs/backend-<env>-<app>.conf   (make sure it has right state file. Otherwise, you may overwrite the existing environment)
./_variables/variables-<env>.conf (make sure the subscription details, and environment details are right.)

Step1: Setup AKS Cluster
./run.sh <env> apply 
./run.sh dev apply

***Note: Make sure "local account" is disabled in AKS cluster, and you (script executore) is a cluster admin. (a member of cluster admin AAD group cloudblogs-aks-cluster-admin)

Step2: Install the base resources
./run.sh <env>-base apply
**base creates the KV where the SSL must be stored for the Ingress Controller to consume. 

Step3: Install Ingress Controller (make sure you have the user nodes created with right labels>> app:cloudblogs)
./run.sh <env>-ingress apply
./run.sh dev-ingress apply



Step4: Verify the KV and Storages are mounting successfully (Optional)
./run.sh <env>-testing apply

## IMPORTANT: Replace Ingress Controller Default SSL (run this command every time you install or update ingress controller)
kubectl patch deployment "ingress-ingress-nginx-controller" \
    -n "ingress" \
    --type "json" \
    --patch '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--default-ssl-certificate=ingress/ingress-tls-secret"}]'

## Setting up an Application on AKS cluster
Step1: Setup App Specific Resources
./run.sh <env>-<app> apply 

Step2: Setup App K8 components into AKS cluster
./run.sh <env>-<app>k8 apply 
Before you run this, make sure the followings:
- required images are copied into ACR
- folders are created on the storage account
- helm values.yaml is updated with right value
